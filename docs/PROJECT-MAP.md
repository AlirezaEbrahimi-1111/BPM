## ۱. پروژه در یک نگاه

سامانهٔ مدیریت فرآیندهای کسب‌وکار (BPM). **PHP خالص، بدون فریمورک**. فرانت‌اند: جاوااسکریپت خالص + Bootstrap 5 (RTL) + AG Grid. دیتابیس: MySQL/MariaDB.

چهار زیرسامانهٔ اصلی:

- **حضور و غیاب** (`attendance_system/`) — زیرسامانهٔ نیمه‌مستقل، ورود/خروج و مرخصی
- **تیکتینگ** (`pages/tickets.php`, `ticket-detail.php`) — پشتیبانی داخلی

## ۲. نقشهٔ ۵ لایه

وقتی باگی می‌بینی، از بالا به پایین دنبالش کن:

| # | لایه | پوشه | نقش |
|---|------|------|-----|
| ۱ | صفحه | `pages/*.php` | HTML + CSS + JS کلاینت. چیزی که کاربر می‌بیند. هر صفحه یک فایل. |

## ۳. چرخهٔ یک درخواست (چطور یک صفحه کار می‌کند)

```
مرورگر  ──GET──▶  pages/foo.php
                    │  require: session_start → config → database → auth → permissions
                    │  اگر لاگین نیست → redirect به index.php
                    │  HTML را چاپ می‌کند، آخرش footer.php
                    ▼
             JS داخل صفحه  ──fetch('/api/foo/bar.php')──▶  api/foo/bar.php
                    │         (هدر: Authorization: Bearer <auth_token از localStorage>)
                    │                                         │ چک توکن، کوئری PDO
                    ▼                                         ▼
             AG Grid / DOM را پر می‌کند  ◀──── JSON: {success, data, ...}
```

نکات کلیدی:
- توکن لاگین در `localStorage` با کلید `auth_token` است. APIها آن را به‌صورت `Bearer` می‌خواهند.
- صفحه‌ها معمولاً `header.php` و `footer.php` را `include` می‌کنند؛ این‌ها CSS/JS مشترک و تم روشن/تاریک را می‌آورند.
- آدرس فایل در تب Network دقیقاً = مسیر فیزیکی فایل در `api/`.

## ۴. چک‌لیست دیباگ — برای هر باگ همین ۶ قدم

1. **مرورگر → F12 → Console** — خطای قرمز JS؟ متنش را بردار.
2. **F12 → Network** — کار را تکرار کن؛ ردیف قرمز (وضعیت ۴۰۰/۵۰۰)؟ کلیک → تب **Response** پیام خطای PHP را دارد.
3. **کدام API؟** آدرس آن ردیف = فایل در `api/`. مستقیم بازش کن.
4. **لاگ سرور** — `d:\Software\xampp\php\logs\php_error_log` (محلی). خطاهای PHP این‌جاست.
5. **تاریخچه** — `git log --oneline -- <file>` و `git blame <file>`؛ کِی و چرا آن خط آمد.
6. **جستجو** — یک متن ثابت از UI را grep کن (مثل «اطلاعیهٔ جدید») تا فایل مربوط پیدا شود.

### تشخیص محلی از واقعی
دیتابیس محلی اغلب از production عقب است (مایگریشن‌ها را معمولاً فقط روی سرور اجرا می‌کنیم). پس **خطای ۵۰۰ محلی روی صفحه‌ای که تازه مایگریشن خورده، لزوماً باگ نیست** — ممکن است ستون/جدول محلی وجود نداشته باشد.

## ۵. مایگریشن‌ها (تغییر ساختار دیتابیس)

- هر فایل: `migrations/YYYYMMDD_HHMMSS_name.php` که آرایه‌ای با `description`, `up`, `down` برمی‌گرداند.
- دستی: `php migrate.php status` / `up` / `up --dry` / `down` — یا از مرورگر `migrate.php?key=SECRET&action=up&dry=1`.
- **روی production لازم نیست دستی بزنی** — workflowِ «Deploy to VPS» خودش در پایانِ کار
  `php migrate.php up` را اجرا می‌کند (بخش ۶ را ببین).
- موتور: `includes/Migrator.php`. جدولِ `schema_migrations` نگه می‌دارد کدام فایل‌ها
  اجرا شده‌اند؛ `up` فقط فایل‌هایِ ثبت‌نشده را اجرا و ثبت می‌کند → **idempotent**، هر بار
  اجرا بی‌خطر است. هر اجرا یک شمارهٔ `batch` می‌گیرد؛ `down` کلِ آخرین batch را برمی‌گرداند.
- DDL در MySQL تراکنشی نیست — اگر یک مایگریشن وسطِ کار خطا بدهد، بخشِ اجراشده برنمی‌گردد؛
  پس `up`/`down` را ساده و قابلِ‌اجرایِ دوباره بنویس (`IF NOT EXISTS` / `IF EXISTS`).

## ۶. دیپلوی و CI/CD (از صفر)

### CI/CD یعنی چه؟
دو تا کارِ تکراری که قبلاً آدم دستی انجام می‌داد، حالا یک ربات خودش انجام می‌دهد:

- **CI = Continuous Integration (یکپارچه‌سازی پیوسته):**
  هر بار کد جدیدی push می‌کنی، یک ربات آن را برمی‌دارد و **چک می‌کند** سالم است یا نه
  (سینتکس درست است؟ تست‌ها پاس می‌شوند؟). هدف: باگ زودتر لو برود، نه بعد از رفتن روی سایت.
- **CD = Continuous Delivery/Deployment (تحویلِ پیوسته):**
  بعد از اینکه CI سبز شد، همان ربات کد را **روی سرورِ واقعی می‌گذارد**. یعنی دیگر خودت
  با FTP فایل کپی نمی‌کنی.

**تشبیه:** CI مثل بازرسِ کنترلِ کیفیتِ کارخانه است که هر محصول را قبل از خروج تست می‌کند.
CD مثل کامیونِ حملی است که محصولِ تأییدشده را به فروشگاه می‌رساند.

### این ربات کجاست؟
**GitHub Actions.** GitHub خودش این سرویس را دارد. تو در پوشهٔ `.github/workflows/`
فایل‌های دستورالعمل (به زبانِ YAML) می‌گذاری؛ GitHub آن‌ها را می‌خواند و اجرا می‌کند.
هر فایل یک **workflow** است. هر workflow از چند **job** و هر job از چند **step** ساخته شده.
GitHub برای اجرا یک کامپیوترِ اجاره‌ایِ موقت (**runner**، معمولاً اوبونتو) روشن می‌کند،
کارها را انجام می‌دهد، بعد خاموشش می‌کند.

### workflowهای این پروژه

| فایل | کِی اجرا می‌شود | چه می‌کند |
|---|---|---|
| `.github/workflows/ci.yml` | **خودکار**، روی هر `git push` به هر شاخه | این‌جا CI است |
| `.github/workflows/deploy.yml` | **فقط دستی** (دکمهٔ Run workflow) | این‌جا CD است |

#### `ci.yml` (خودکار)
`on: push` → با هر push خودش راه می‌افتد. مراحلش:
1. کدِ push‌شده را چک‌اوت می‌کند.
2. PHP نسخهٔ ۷.۴ نصب می‌کند (همان نسخهٔ سرورِ production — تا اگر چیزی محلی کار می‌کند
   ولی روی ۷.۴ نه، همین‌جا لو برود).
3. `php -l` روی **همهٔ** فایل‌های `.php` (چکِ سینتکس).
4. `php tests/run.php unit` (تست‌های یونیت).

خروجی: یک تیکِ سبز ✅ یا ضربدرِ قرمز ❌ کنارِ کامیت در GitHub. قرمز = یک فایل سینتکسِ
خراب دارد یا یک تست شکسته. **هیچ چیزی دیپلوی نمی‌کند** — فقط خبر می‌دهد.

**دقیقاً چه چیزی تست می‌شود؟** CI فقط هر فایلی که در `tests/unit/` باشد را اجرا می‌کند —
مرجعِ بیرونی‌ای نیست؛ خودمان تصمیم می‌گیریم کدام رفتار مهم است. الان:

| فایل | چه رفتاری را قفل نگه می‌دارد |
|---|---|
| `tests/unit/WorkingDaysTest.php` | محاسبهٔ روزهای کاری (حذفِ جمعه و تعطیلات) |
| `tests/unit/PermissionsTest.php` | منطقِ نقش‌ها/دسترسی در `permissions.php` |
| `tests/unit/ManagerScopeTest.php` | «یک مدیر چه کسانی را می‌بیند» (`getSubordinateIds` / `canManageTargetUser`) |

این تست‌ها به دیتابیسِ واقعی وصل نمی‌شوند — هرکدام یک SQLiteِ درون‌حافظه‌ای می‌سازند،
چند ردیفِ نمونه می‌ریزند و خروجیِ تابع را با مقدارِ انتظاری مقایسه می‌کنند. سریع و ایزوله.
`tests/integration/` هم هست ولی CI اجرایش نمی‌کند (به سرورِ زنده + توکن نیاز دارد).
اگر فردا `tests/unit/FooTest.php` اضافه کنیم، CI خودبه‌خود اجرایش می‌کند — بدونِ تغییرِ `ci.yml`.

#### `deploy.yml` — «Deploy to VPS» (دستی)
`on: workflow_dispatch` → یعنی «فقط وقتی آدم دستی دکمه بزند». عمداً دستی است تا کنترلِ
لحظهٔ رفتنِ تغییر روی سایتِ زنده دستِ خودت باشد.

**چطور اجرا کنی:** GitHub → تبِ **Actions** → از لیستِ چپ «Deploy to VPS» → دکمهٔ
**Run workflow** → دوباره **Run workflow**.

بعد runner با SSH (یک اتصالِ امن به سرور) وصل می‌شود و این دو دستور را روی خودِ سرور
اجرا می‌کند:
```
deploy-update                                          # اسکریپتِ سروری: git pull + تنظیمِ دسترسیِ فایل‌ها
sudo -u www-data php /var/www/itmalek/migrate.php up   # مایگریشن‌های در انتظار
```
یعنی یک کلیک = هم کدِ جدید می‌رود، هم دیتابیس جلو می‌آید. **نیازی به SSH یا دستورِ دستی نیست.**

کلیدهای اتصال (host/user/ssh key) در GitHub به‌صورتِ **Secret** ذخیره شده‌اند
(`Settings → Secrets`)، در کد نیستند.

#### زدنِ «Run» چطور یک فایل را روی سرورِ من اجرا می‌کند؟
دکمه **مستقیماً** به سرورِ تو دست نمی‌زند. زنجیره این است:

1. دکمه را می‌زنی → به GitHub می‌گویی «`deploy.yml` را اجرا کن».
2. GitHub یک **runner** (اوبونتوی موقت، در ابرِ خودش) روشن می‌کند.
3. runner فایل را می‌خواند؛ به قدمِ `uses: appleboy/ssh-action` می‌رسد — ابزاری که
   کارش فقط «از runner یک اتصالِ SSH به یک سرورِ دیگر باز کن» است.
4. این ابزار با `host`/`username`/`key` (از Secretها) به سرورِ تو **SSH می‌زند** — دقیقاً
   مثلِ اینکه خودت یک ترمینال باز کرده و به سرور لاگین کرده باشی.
5. روی همان اتصال، دستورهای بخشِ `script:` را **روی خودِ سرورِ تو تایپ و اجرا می‌کند**
   (`deploy-update` و `migrate.php up`).
6. کار تمام → runner خاموش می‌شود.

**تشبیه:** یک پیکِ مطمئن (runner) استخدام کرده‌ای و یک کلیدِ خانه‌ات را در گاوصندوقِ
GitHub (Secret) گذاشته‌ای. می‌گویی «برو» → پیک می‌رود، با کلید در را باز می‌کند، لیستِ
کارها را انجام می‌دهد، قفل می‌کند و می‌رود. خودت رانندگی نکردی.

> ⚠️ `tests/run.php` را با `migrate.php` قاطی نکن: `run.php` مالِ **CI** است و روی
> runnerِ GitHub با SQLiteِ قلابی اجرا می‌شود؛ `migrate.php` مالِ **Deploy** است و
> روی سرورِ خودت با دیتابیسِ واقعی اجرا می‌شود.

### روالِ کاملِ یک تغییر
```
۱. کد را عوض می‌کنی
۲. git commit  →  git push
۳. CI خودش اجرا می‌شود → منتظرِ تیکِ سبز بمان
۴. تبِ Actions → Deploy to VPS → Run workflow
۵. لاگِ اجرا را نگاه کن: کد رفت؟ مایگریشن (اگر بود) اجرا شد؟
```

سرور production: `185.213.195.192` (مسیر: `/var/www/itmalek`).

### واژه‌نامهٔ کوتاه
- **workflow**: یک فایلِ دستورالعمل در `.github/workflows/`.
- **job / step**: یک workflow از چند job، هر job از چند step (دستور).
- **runner**: کامپیوترِ موقتی که GitHub برای اجرا روشن می‌کند.
- **trigger** (`on:`): چیزی که workflow را راه می‌اندازد — `push` (خودکار) یا
  `workflow_dispatch` (دستی).
- **secret**: مقدارِ محرمانه (رمز/کلید) که در تنظیماتِ GitHub ذخیره می‌شود، نه در کد.
- **SSH**: پروتکلِ اتصالِ امن به یک سرورِ راه‌دور.
- **YAML**: زبانِ سادهٔ نوشتنِ این فایل‌ها (با تورفتگی، شبیهِ لیست).

## ۷. قواعد پروژه (فهرست در حال رشد)

- **تاریخ/ساعت همیشه از سرور** — نه از دستگاه کاربر. در JS از `assets/js/time-sync.js` (`TimeSync.serverNow()`, `formatJalali()`, `timeAgo()`...) استفاده کن، نه `new Date()`.
- **ارقام فارسی در UI** — اعداد نمایشی باید فارسی باشند. هر صفحه معمولاً هِلپر محلی خودش را دارد (`toPersian`, `convertToFarsiNumber`, `farsi`).
- **JS مشترک** — فایل‌های داخل `assets/js/` که در چند صفحه لود می‌شوند نباید `let`/`const` در سطح بالا داشته باشند (تداخل هنگام دابل‌لود)؛ فقط `function` / `var` و گارد `if (typeof X === 'undefined')`.
- **محاسبهٔ تأخیر** — همیشه با روزهای کاری (جمعه + تعطیلات حذف)، نه اختلاف تقویمی خام. → `working-days-helper.php`.
- **چک‌باکس دسترسی/مجوز** — به‌صورت سوییچ Bootstrap، کنار هم، با فاصلهٔ کم.
- **تم تاریک** — هر CSS جدید باید حالت `:root[data-theme="dark"]` را هم داشته باشد.
- **تفکیک سازمان‌ها** — دادهٔ هر سازمان محرمانه است و نباید با سازمان دیگر قاطی شود؛ کوئری‌ها باید `organization_id` را فیلتر کنند.
- **رنگ‌ها** — پالت اصلی در `assets/css/custom.css` با متغیرهای CSS (`--primary` و ...).

## ۸. دیتابیس: چرا MySQL/MariaDB؟

### چرا SQL و نه NoSQL
دادهٔ این پروژه کاملاً **رابطه‌ای** است: کاربر ← سازمان، کار ← ارجاع‌ها ← چک‌لیست،
تیکت ← پیام‌ها، روتین ← مراحل. همه‌چیز جدول است با کلید خارجی و `JOIN`. برای این
شکل داده، پایگاه‌دادهٔ SQL انتخابِ طبیعی است.

| گزینه | چرا انتخاب نشد |
|---|---|
| MongoDB (سندی/NoSQL) | برای دادهٔ بی‌ساختار خوب است؛ این‌جا روابط سفت‌وسخت داریم و باید دستی شبیه‌سازی می‌شد. |
| PostgreSQL | انتخاب فنیِ خوبی بود، ولی MySQL/MariaDB روی XAMPP و هاست‌های معمولی پیش‌فرض و در دسترس‌تر است؛ اکوسیستم PHP هم سنتاً با MySQL جفت شده. |
| SQLite | تک‌فایل بدون سرور — برای اپ سبک/تک‌کاربره؛ برای نوشتنِ هم‌زمانِ چند کاربر مناسب نیست (قفلِ کلِ فایل). |

اتصال در `config/database.php` با درایورِ `pdo_mysql` و DSNِ `mysql:host=...` است.

### MariaDB در برابر MySQL
- MySQL را Oracle خرید (۲۰۱۰)؛ سازندهٔ اصلی یک انشعابِ آزاد ساخت: **MariaDB**.
- MariaDB تقریباً **جایگزینِ مستقیم (drop-in)** است: همان پروتکل، همان SQL، همان درایورِ
  `pdo_mysql`. کدِ پروژه نمی‌فهمد کدام‌یک زیرش است.
- تفاوت‌ها جزئی: MariaDB کاملاً متن‌باز است، چند تابع/موتورِ اضافه دارد، گاهی سریع‌تر.
- **چرا این پروژه MariaDB دارد:** XAMPP چند سالی است به‌جای MySQL، MariaDB را بسته‌بندی
  می‌کند. انتخابِ آگاهانه نبود — چیزی بود که ابزارها آوردند؛ و چون سازگارند مشکلی نیست.

## ۹. برگشت به عقب (کد و دیتابیس)

**کد و دیتابیس دو چیزِ جدا هستند و جدا برگردانده می‌شوند. باید هماهنگ باشند.**

### کد ← با Git
```bash
git revert <hash>     # یک کامیتِ «معکوس» می‌سازد (امن؛ تاریخچه پاک نمی‌شود) — توصیه‌شده
git push
# سپس دوباره: Actions → Deploy to VPS → Run workflow
```
`git revert` بهتر از `git reset --hard` است چون چیزی را پاک نمی‌کند.

### دیتابیس ← با migrate.php (نه گیت‌هاب!)
```bash
php migrate.php down   # روی سرور، با SSH — تابعِ down آخرین batch را اجرا می‌کند
```
**رفتن به جلو خودکار است (workflowِ دیپلوی)، ولی برگشت به عقب دستی است.** باید با SSH
به سرور وصل شوی و `down` بزنی. Git هیچ کاری با ساختارِ دیتابیسِ روی سرور ندارد — حتی اگر
فایلِ مایگریشن را از گیت پاک کنی، جدول/ستونِ ساخته‌شده سرِ جایش می‌ماند تا `down` را بزنی.

### ترتیبِ درستِ برگشت
1. اول `php migrate.php down` (دیتابیس به عقب)
2. بعد `git revert` + Deploy (کد به عقب)

اگر کد را عقب ببری ولی دیتابیس جلو بماند (یا برعکس)، خطای «ستون/جدول ناموجود» می‌گیری.

## ۱۰. احراز هویت (Authentication) — از صفر

### واژه‌ها
- **Authentication (احراز هویت):** «تو کی هستی؟» — چکِ نام‌کاربری/رمز.
- **Authorization (اجازه‌دهی):** «حالا که می‌دانیم کی هستی، اجازهٔ این کار را داری؟» —
  این‌جا کارِ `includes/permissions.php` است (نقش‌ها). با هم قاطی نشوند.
- **Hash:** تبدیلِ یک‌طرفهٔ رمز به یک رشتهٔ نامفهوم. از هش نمی‌شود رمز را برگرداند.
- **JWT (JSON Web Token):** یک «کارتِ شناساییِ امضاشده». سه بخش با نقطه جدا شده:
  `header.payload.signature`. payload یک JSON است (id کاربر، انقضا و...). signature
  با یک کلیدِ محرمانه ساخته می‌شود؛ هرکس payload را دست بزند، signature دیگر نمی‌خواند.
- **Bearer token:** توکن در هدرِ درخواست: `Authorization: Bearer <توکن>`.

### رمزِ عبور
- موقعِ ثبت‌نام/تغییرِ رمز: `password_hash($pw, PASSWORD_DEFAULT)` (الگوریتمِ bcrypt) →
  در `users.password` ذخیره می‌شود. **رمزِ خام هیچ‌جا ذخیره نمی‌شود.**
- موقعِ ورود: `password_verify($pw, $user['password'])`.
- `api/auth/login.php` قبلِ چکِ رمز، **rate limit** دارد: بیش از ۵ تلاشِ ناموفق در ۱۵
  دقیقه (بر اساسِ IP یا نامِ کاربری) → قفلِ موقت (جدولِ `login_attempts`).
- ورود می‌تواند با **OTP** (کدِ پیامکی) هم باشد — همان endpoint، `action: 'send_otp'` / `'verify_otp'`.

### توکن — ساخت (`Auth::generateJWTToken`)
payload:
```json
{ "user_id": 12, "organization_id": 3, "tv": 4, "iat": ..., "exp": ... }
```
- `tv` = `token_version` کاربر از جدولِ `users` (کاربردش پایین).
- `exp` = زمانِ انقضا: **۵ ساعت** به‌صورتِ عادی، **۳۰ روز** با تیکِ «مرا به خاطر بسپار».
- امضا: `hash_hmac('sha256', header.payload, JWT_SECRET)`.
- `JWT_SECRET` از `config/config.php` می‌آید که `.gitignore` شده — در گیت نیست.

### ذخیره‌سازی
| کجا | چه چیزی | توضیح |
|---|---|---|
| مرورگر — `localStorage['auth_token']` | خودِ JWT | با `fetch` به APIها فرستاده می‌شود |
| مرورگر — `localStorage['user_info']` | JSONِ کاربر (id، نقش، نام...) | فقط برای نمایشِ سریعِ UI؛ **مرجعِ امنیتی نیست** |
| مرورگر — کوکیِ نشستِ PHP | `PHPSESSID` | برای **بارگذاریِ کاملِ صفحه** (که هدرِ Bearer ندارد) |
| سرور — `users.token_version` | یک عددِ شمارنده | ابزارِ باطل‌کردنِ توکن (پایین) |
| سرور — جدولِ `login_attempts` | تلاش‌های ناموفق | برای rate limit |

خودِ JWT روی سرور **ذخیره نمی‌شود** — «بی‌حالت» (stateless) است؛ سرور فقط امضایش را
دوباره حساب می‌کند.

### هر درخواست چطور چک می‌شود
**فراخوانیِ API (با `fetch`):** کلاینت هدرِ `Authorization: Bearer <token>` می‌گذارد.
سمتِ سرور `Auth::getUserFromToken()` → `extractToken()` (هدر را می‌خواند) →
`validateToken()`:
1. توکن سه‌تکه است؟
2. امضا را با `JWT_SECRET` دوباره بساز و با `hash_equals` مقایسه کن → اگر فرق داشت،
   یعنی دست‌کاری شده → رد.
3. `exp` گذشته؟ → رد.
4. کوئری به `users`: `is_active = 1` **و** `token_version`ِ دیتابیس == `tv`ِ داخلِ توکن؟
   → اگر نه، رد.
5. `user_id` را برگردان (یا `false`).

**بارگذاریِ کاملِ صفحه (مثلاً باز کردنِ `pages/tasks.php`):** مرورگر هدرِ Bearer
نمی‌فرستد. صفحه اول `$_SESSION['user_id']` را چک می‌کند (که `api/auth/set-session.php`
بعد از ورود پُر کرده)، بعد Bearer، بعد یک کوکیِ `auth_token` (فالبکِ قدیمی). هیچ‌کدام
نبود → `header('Location: ../index.php')`.

### باطل‌کردنِ توکن (Logout / تغییرِ رمز / غیرفعال‌سازی)
JWTِ ساده را نمی‌شود پس گرفت. ترفندِ این پروژه: با هر خروج/تغییرِ رمز،
`users.token_version` **یکی زیاد می‌شود**. آن‌وقت مرحلهٔ ۴ِ بالا برای همهٔ توکن‌های
قبلی شکست می‌خورد → همه فوراً بی‌اعتبار.

### چرا گاهی «صفحهٔ خالی» می‌شد؟
توکن در `localStorage` بود ولی سرور ردش می‌کرد (منقضی یا `token_version` بالا رفته).
هدر حالا روی **۴۰۱ از `api/header/bootstrap.php`** توکن را پاک و به لاگین ریدایرکت
می‌کند (`hdrHandleAuthFailure` در `pages/header.php`).

### فایل‌های کلیدی
`includes/auth.php` (کلاسِ `Auth`) · `api/auth/login.php` · `api/auth/logout.php` ·
`api/auth/set-session.php` · `config/config.php` (`jwt_secret`) · `includes/permissions.php` (اجازه‌دهی).

### همین بخش، به زبانِ خیلی ساده (مثالِ شهربازی)

| در شهربازی | در پروژه |
|---|---|
| رمزت را در ماشین می‌ریزند → `7xQp29` و فقط همین ذخیره می‌شود | `password_hash()` → ستونِ `users.password` |
| مقایسهٔ رمزِ واردشده با نسخهٔ ذخیره‌شده | `password_verify()` |
| مُهرِ نامرئیِ روی دست (نوشته: کی هستی + تا کِی معتبر) | توکن (JWT) |
| جوهرِ مخصوصِ شهربازی که کسی نمی‌تواند تقلید کند | `JWT_SECRET` در `config/config.php` |
| دستت (جای نگهداریِ مُهر) | `localStorage['auth_token']` در مرورگر |
| سه چکِ مسئولِ هر بازی: مُهر واقعی؟ تاریخ نگذشته؟ لیستِ اخراجی‌ها؟ | `validateToken()`: امضا، `exp`، کوئریِ `users` (`is_active` + `token_version`) |
| شمارهٔ روی مُهر که با هر خروج/تغییرِ رمز در دفتر یکی زیاد می‌شود و مُهرِ قدیمی را می‌کُشد | `users.token_version` (فیلدِ `tv` در توکن) |
| بلیتِ رختکن که مرورگر خودکار همراه دارد | کوکیِ `PHPSESSID` |

### توکن یا session؟ خطِ جداکننده

مهم نیست چطور به صفحه رسیدی (لینک، آدرس، رفرش، بوکمارک). مهم این است **چه اتفاقی می‌افتد**:

| اتفاق | با چه چیزی چک می‌شود | چرا |
|---|---|---|
| **گرفتنِ خودِ صفحه** (HTML) از سرور | کوکیِ `PHPSESSID` (session) | هیچ JSای اجرا نمی‌شود که توکن را بچسباند؛ فقط کوکی خودکار می‌رود |
| **بعد از باز شدنِ صفحه**، وقتی JS آن می‌رود داده بگیرد (`fetch`) | توکن از `localStorage` | حالا JS اجرا می‌شود و خودش توکن را در هدرِ `Authorization` می‌گذارد |

**نمونهٔ ترتیب** — سارا روی «کارها» کلیک می‌کند:
1. مرورگر `pages/tasks.php` را از سرور می‌خواهد + خودکار کوکیِ `PHPSESSID`. (توکن نمی‌رود.)
2. سرور کوکی → session → «ساراست» → HTMLِ صفحه را می‌فرستد. (نبودِ session → ریدایرکت به لاگین.)
3. صفحه باز می‌شود، JSاش شروع می‌کند.
4. JS: `fetch('/api/tasks/list.php', { headers:{ Authorization: 'Bearer ' + localStorage.auth_token }})`.
5. سرور توکن را از هدر می‌خواند → `validateToken` → لیستِ کارها را JSON می‌دهد.
6. JS کارها را در صفحه می‌چیند.
